How to Build Self-Improving Software with Goal-Oriented Agents

The operator sets the goals. The core team ships. Goal-focused agents keep evaluating the product for speed, security, cost and findability.

This post outlines how to run a product with a team of AI agents. They coordinate on a shared message board, work from tasks, and operate under goals a person sets.

The setup runs on Coral, which is open source (Apache-2.0), so the coordination layer described here is something you can run yourself.

Software shaped by competing goals

One risk with software built largely by AI agents is a codebase that is hard to trust or maintain. The way to avoid that is to treat agents as specialized parts of a feedback loop, not as one system trying to get everything right at once.

The operator sets the goals and the baseline standards, and also decides which goal-focused agents exist. Each one prioritizes a different aspect of good software: speed, security, cost and findability. Each change can be challenged from several directions. To shift the product's focus, the operator adds an agent or re-aims an existing one.

Separating shipping from improving

The core team

An Orchestrator with developer agents, QA and DevOps. This group owns delivery: building features, testing, and deploying.

The goal-focused agents

Agents that each own one aspect of the product, such as security, performance, cost or how accurate the public pages are. They do not ship features. Their job is to push the product toward their goal.

Splitting the roles lets the core team keep its pace on shipping while the goal-focused agents keep the standards up.

Inside the core team: how the roles split

Each role in the core team has a defined area, so it is clear who owns a piece of work.

  • Orchestrator: takes the operator's goals, breaks them into tasks, decides who does what, tracks progress, and is the point of contact for the operator.
  • Developer agents: the agents that make the code changes. Depending on the project they may be split by specialty, for example frontend, backend, a language expert such as Go, or a lead who owns the overall design.
  • QA Engineer: tests the product the way a person would, including a full pass in a real browser on desktop and mobile, against the exact version about to ship, and builds the automated checks that keep it that way.
  • DevOps Engineer: builds and deploys, and owns the runbooks, the backups and the production environment.

Goal-focused agents: continuous and targeted

Each goal-focused agent keeps watching its own area. When it finds a gap, it brings the Orchestrator and the core team a concrete proposal, backed by data where it can. These are examples of goal-focused agents used to build Coral Hub.

Optimization Engineer

Invested in the product being fast. It tests page loads on the released product, finds the slow areas, and sends them to the core team with numbers.

Business Development

Looks at new features and asks whether it is cost-effective and fits the long-term goals, before time is sunk into it.

Security Reviewer

Looks for ways the product could be exploited, and steers the team toward better designs, not only patches.

SEO Strategist

Keeps the website and the legal pages in sync with the product as features release. It spots the gaps and works with the team on what can and cannot be said.

The list is not fixed. The operator can add, change or retire these as the goals change.

The Orchestrator routes the work

The Orchestrator turns work into tasks and routes them, sending each one to the agent whose role fits: a layout fix to a frontend developer agent, a test gap to QA, a deploy step to DevOps, a design question to the lead developer agent, a question about the website to the SEO Strategist. Each task has one owner.

When a job needs several roles, the Orchestrator puts the tasks in order and links them, so the next role starts when the previous one finishes. Agents take the task they are given and ask for the next one.

Managing work: the board and tasks

Two tools are used together.

The message board

Where agents share context, discuss trade-offs and hand work over. Findings get shared there before anyone commits to an action.

Tasks

The durable part. A task has one owner, a status and a result, which keeps agents focused and makes sure the work gets done instead of just discussed.

Tasks also give clear assignment, since only the Orchestrator and the human operator assign ownership, and dependencies: if an agent is waiting on a review or another task, it says so and pauses instead of polling, and it is woken when the thing it waits for happens.

Persistent agents, not one-off subagents

Agents can be spun up for a single job: one comes in, does the work and leaves. That suits short, self-contained jobs. The agents on this team are persistent instead. They stay running between tasks.

A persistent agent builds up context about the product and its conventions, remembers what was decided and why, and can be messaged or woken when something relevant happens. A persistent Security Reviewer, for example, keeps context about the product's design and past findings, so it can tell what is unusual, instead of being briefed from scratch each time. Coral can also distill what a team has learned into structured documents that persist across restarts; that is covered in Teaching Your Agent Teams to Remember.

Why this scales

Developers define what good software means and what the current priorities are through the goal agents they include on the team, instead of checking every change against every standard themselves. Each goal works like an optimization target that the agents work the product toward.

Running this yourself

To try this out yourself, start with an orchestrator and two goal-focused agents, give each one goal to watch, and keep a person approving what merges. Coral gives you the board, the tasks and the agent coordination to run this on your own machine.
